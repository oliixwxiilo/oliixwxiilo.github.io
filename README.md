## 一、上传目录

日常添加插件时，将文件放入对应目录，并提交到 `main` 分支。

| 内容 | 上传目录 | 支持格式 / 用途 |
| --- | --- | --- |
| 插件安装包 | `pool/main/` | 当前发布版本，上传 `.deb` |
| 插件图标 | `assets/icons/` | `.png`、`.jpg`、`.jpeg`、`.webp` |
| 插件资料 | `metadata/packages/` | 可选的 `.json` 文件，用于补充介绍、系统支持、更新日志等 |
| 历史版本安装包 | `pool/old/插件名称/` | 需要保留的旧版 `.deb` |

**截图功能已取消。** 不需要上传插件截图，也不需要创建截图目录或在资料中配置截图。

## 二、最简单的上传方式

只发布一个普通插件时，通常只需要：

1. 将插件的 `.deb` 安装包上传到 `pool/main/`。
2. （可选）将图标上传到 `assets/icons/`。
3. 将文件提交到仓库的 `main` 分支。

不需要手动生成 `Packages`、`Release`，也不要求每个插件都创建 JSON 资料文件。

## 三、图标自动关联规则

构建程序会读取安装包内部的包标识和显示名称，在 `assets/icons/` 中自动寻找匹配图标。匹配时会尝试：

- 完整软件包标识，例如 `com.example.demo.png`；
- 软件包标识最后一段，例如包标识 `xyz.cypwn.killbackground13` 可匹配 `KillBackground13.png`；
- 插件显示名称，例如 `番茄音乐.png`。

匹配时会忽略大小写及常见标点差异。建议图标文件名尽量使用上述名称之一。找不到匹配图标时，插件仍可正常生成索引，只是不显示仓库单独提供的图标。

## 四、插件资料 JSON（可选）

没有 JSON 时，构建程序会从 `.deb` 中读取包标识、名称、版本、架构、依赖等信息，生成基础插件详情。安装包大小按实际 `.deb` 文件体积自动计算并显示为 KB/MB；架构直接读取 `Architecture` 字段；系统要求优先读取 `Firmware`、`MinOSVersion`、`MinimumOSVersion`、`iOS-Version` 等控制字段。若安装包未声明系统要求且 JSON 也未补充，则显示“安装包未注明”，不会自行推断。

如果需要自定义中文名称、介绍或更新日志，可在 `metadata/packages/` 中创建 JSON 文件。系统支持信息优先从安装包控制字段自动读取；仅当安装包没有声明系统要求时，才使用 JSON 中手动填写的“支持的系统”作为补充。文件名可以自定，内容示例：

```json
{
  "软件包标识": "com.example.demo",
  "插件名称": "示例插件",
  "当前版本": "1.0",
  "插件介绍": "这里填写插件介绍。",
  "支持的系统": "iOS 15 至最新越狱系统",
  "上传日期": "2026-11-25",
  "更新日志": [
    {
      "版本": "1.0",
      "日期": "2026-11-25",
      "内容": [
        "首次发布"
      ]
    }
  ]
}
```

注意：
- `软件包标识` 必须与安装包内部的 `Package` 字段完全一致。
- `当前版本` 建议与安装包内部版本号保持一致。
- `插件图标` 可选；如需手动指定，填写仓库内相对路径，例如 `assets/icons/demo.png`。正常情况下优先使用自动匹配即可。
- `更新日志` 的 `内容` 使用字符串数组。
- 不要填写截图字段；当前详情页不再生成或展示插件截图。

## 五、历史版本

将需要保留的旧版 `.deb` 放到 `pool/old/插件名称/`。构建程序会扫描当前版本和历史版本安装包并生成索引。

如需在插件详情中显示指定的历史版本下载入口，可在对应 JSON 中增加：

```json
{
  "软件包标识": "com.example.demo",
  "旧版本下载": [
    {
      "版本": "0.9",
      "安装包路径": "pool/old/示例插件/com.example.demo_0.9_iphoneos-arm64.deb"
    }
  ]
}
```

路径必须与仓库中的实际文件路径一致。

## 六、自动构建与部署

仓库的 GitHub Actions 工作流会在以下情况自动运行：

- 向 `main` 分支推送提交；
- 在 GitHub Actions 页面手动运行工作流。

自动流程会：

1. 扫描 `pool/main/` 和 `pool/old/` 中的 `.deb` 文件。
2. 读取安装包控制信息，检查包标识、版本和架构。
3. 自动关联图标，并读取可选的 JSON 插件资料。\n4. 自动计算安装包大小，并从安装包控制信息读取系统要求与架构。
4. 生成 Sileo 插件详情 JSON 和网页详情页。
5. 生成 `Packages`、`Packages.gz`、`Packages.xz`，并将常见软件包分类名称转换为中文（例如 Tweaks 显示为“插件”、Themes 显示为“主题”）。
6. 重新生成 `Release` 文件及对应校验哈希。
7. 将仓库内容部署到 GitHub Pages。

当前支持 `iphoneos-arm64`、`iphoneos-arm64e` 和 `all` 三种安装包架构。构建程序会分别生成 `binary-iphoneos-arm64` 与 `binary-iphoneos-arm64e` 索引；架构为 `all` 的通用安装包会同时加入两个索引。根目录的扁平兼容索引同时包含 arm64 与 arm64e 记录，并在根目录 Release 中声明两种架构；APT 会按设备架构筛选。标准 dists 架构索引仍然彼此独立，不会互相混入。其他架构的安装包会被跳过。如果仓库中没有可发布的支持架构安装包，或发现重复的软件包版本，构建会报错并停止部署。

## 七、如何确认部署成功

提交文件后，打开 GitHub 仓库的 **Actions** 页面，查看最新的“构建软件源并部署网站”任务：

- **构建步骤成功**：说明安装包解析和索引、详情生成通过。
- **部署到 GitHub Pages 步骤成功**：才表示网站和软件源已完成发布。
- 如果任务失败，打开对应任务查看日志，按报错修正后重新提交。

请注意：文件上传成功不等于网站已经部署成功。只有 Actions 中部署步骤成功后，再刷新 Sileo、Zebra 等软件包管理器验证最终显示。

## 八、维护注意事项

- 必须提交到 `main` 分支才能触发当前自动部署工作流。
- 新插件最少只需上传一个有效的 `.deb` 安装包。
- 图标是可选项；推荐与包标识或插件名称匹配，便于自动关联。
- JSON 是可选项；仅在需要补充介绍、系统支持、更新日志或历史版本入口时使用。
- 不要手动修改自动生成的 `Packages`、压缩索引和 `Release` 文件，它们会在每次构建时重新生成。
- 插件截图功能已经移除，后续无需上传或维护截图文件。
